# 07 · v3.0 入库审核流：AI 预筛 + 人工把关（2026-09-05）

> 目标：解决「什么垃圾文档都能进索引」的问题——扫描件、乱码、空白表单直接入库会污染检索结果。设计原则：**AI 打分预筛 + 人工把关兜底 + 双层存储隔离**。

## 一、为什么做审核流

- 真实语料质量参差：有扫描件/乱码文本、有空表格、有重复内容；
- 入库即参与检索：一份烂文档会持续污染 N 次问答的上下文；
- 企业场景诉求「管得住」：入库要有质量门槛，且门槛要**可解释、可人工干预**。

## 二、关键设计与决策

### 1. 文档质量打分器（`src/review/scorer.py`）

四维规则评估，输出 0-100 分 + 扣分原因：

| 维度 | 拦截目标 |
|------|---------|
| 长度合理区 | 过短空洞文件 |
| 文本密度 | 扫描件、乱码 |
| 结构完整度 | 章节条款识别，缺结构的碎片 |
| 清洗损失率 | 清洗前后字符数比值——清洗掉太多说明原文脏 |

**决策**：打分器纯规则、零 LLM、离线可跑——可测试、可解释（每分都有扣分原因）、不依赖模型。

### 2. 审核状态机（`src/review/store.py`）

```
pending_score → pending_review → approved / rejected
```

- JSON 原子写持久化（沿袭 v2.3.1 规约）；
- **双层存储** `tier = raw | highlight`：待审/退回文档仅留原文缓存（`data/raw_docs/`，不占索引资源），过审才晋升亮点层参与检索——审核不阻塞、不污染。

### 3. 入库链路改造

- 上传与批量入库统一走 `process_and_ingest`：打分达阈值（默认 60，`REVIEW_SCORE_THRESHOLD` 可配）直接生效；低分挂起待人工审；
- `REVIEW_MODE`: threshold（默认）/ all（全部人工审）/ off。

### 4. 审核 API（`serve/routers/review.py`）

- 队列按**分数升序（最差在前）**——人工先看最烂的；
- 入库前后对比 diff（清洗前原文 vs 清洗后切片 + 损失率）；
- approve（重切片带标注入库）/ reject（**已生效文档同步移出索引**）/ annotate（chunk 级标注）/ stats。

### 5. 人工标注检索加权（点睛之笔）

- 标注过的分片 RRF 融合后按 `score × (1 + 0.2)` 加权（`HIGHLIGHT_WEIGHT`），回答来源带 `highlighted` 徽章；
- 效果：**人审核一次，AI 长期受益**——审核从成本项变成检索质量资产。

## 三、联动与伏笔

- 删除文档联动清理审核记录与原文缓存（不留孤儿数据）；
- 伏笔：语料里两份空白表单模板（171/594 字）在 v3.1.0 支持 .xlsx 后正好被按「长度合理区」自动判低分挂起——**审核流与格式扩展零特判衔接**，见 [08 篇](./08-v3.0.1-v3.1-静默丢弃修复与格式扩展.md)。

## 四、产出物

`src/review/`（scorer/store）；统一入库入口 `process_and_ingest`；6 个审核 API；双层存储 + 原文缓存目录；标注加权与徽章；新增 `tests/test_review.py` **15 个用例，累计 67 测试全离线通过**。

## 五、教训与规约

1. **质量门槛要「AI 预筛 + 人工兜底」分工**，不是二选一：规则打分挡掉 80% 明显垃圾，人只看边界 case；
2. 打分必须可解释——只有分数没有原因，人工审核没法建立对 AI 的信任；
3. 双层存储让「待审」与「在检索」物理隔离，审核流程永远不会让烂文档短暂可用；
4. 人工动作（标注）要反哺系统（加权），否则审核只是闸门不是资产；
5. reject 已生效文档要同步移出索引——状态机变更必须核对所有下游存储。
