# 05 · v2.4~v2.6 模型接入与问答体验重构（2026-08-30）

> 目标：一天五连发（v2.4/v2.5/v2.5.1/v2.6）。核心两件事：接入小米 MiMo 并把模型配置做成**在线热切换**；治理流式问答「首字卡 30 秒」的头号体验痛点。本篇不覆盖两个深坑（chroma 不落盘 / 流程图提取），见 [06 篇](./06-深坑实录-chroma不落盘与流程图提取.md)。

## 一、阶段目标

1. 多服务商 LLM 接入：换模型不重启、不删库、不改调用方；
2. 流式延迟治理：把「30s+ 静默等待」压到秒级可感知；
3. 固定流程（请假/报销等）从「一句话直接开单」改为结构化确认闭环；
4. 容量兜底：千份文档入库要心里有数。

## 二、关键动作与决策

### 1. MiMo 接入与模型配置面板（v2.4.0）

- `LLMManager.PROVIDERS` 注册 mimo（OpenAI 兼容），主模型切 `mimo-v2.5-pro`，全链路 + SSE 流式实测通过；
- **思考模式约束**：MiMo 思考模式不支持自定义 temperature（强制 1.0）——在 `models/llm.py` 按模型名自动处理，不靠人记；
- 前端面板重构：顶部常显「当前生效」状态；**测试与保存职责分离**——`/api/model/test` 纯连通性测试（返回耗时，不落盘），通过后点「保存并生效」才写配置，保存即生效无需重启；模型输入框接 datalist + `/api/model/models` 拉取该 Key 全部可用模型（仅 admin）。

### 2. 流式卡顿治理（v2.5.0，方法论样本）

**先测量定位**：首字前要串行执行「指代消解 + 查询改写」两次 LLM 调用，MiMo 思考模型下单次 7~12s——瓶颈是调用次数与思考 token，不是网络。

四步拆解：

1. **关思考**：实测 `thinking: {"type":"disabled"}` 有效——辅助调用 12s → 6.8s 且无 reasoning 输出；新增 `LLM_THINKING` 配置（默认 off）；
2. **减调用**：指代消解 + 查询改写合并为单次调用（`prepare_query`）；无历史时零 LLM 开销；
3. **可视化**：SSE 推送「理解问题 → 检索知识库 → 生成回答」阶段状态与耗时，等待不再黑盒；
4. **精简输出**：QA 提示词重写（结论先行、3~6 条要点 ≤200 字、禁客套话），病假问题回答从大段落降为 73 字要点。

**实测结果：多轮追问（含指代）端到端 6.9s（优化前该路径仅前置调用就需 20s+）。**

### 3. 流程确认闭环（v2.5.0）

- 新增 `workflow_chain.py`：按流程字段 Schema 用 `with_structured_output` 提取参数，无 LLM 正则兜底；
- `/agent` 的 action 意图从「直接 launch」改为返回**草稿**；新增 `workflow/draft` + `workflow/submit`（必填校验 + 定向提交）；
- 前端渲染确认表单卡片：预填已识别信息、高亮缺失必填、可修改后提交；
- 实测：「帮我请个年假，9月3日到9月5日，家里有事」→ 类型/起止/事由全识别 → 确认提交 → 工单 `WK-CDFCF6CA03`。

### 4. 同日补充件

- **推荐追问**：回答完成后基于本次问答生成 3 个追问（`followups` SSE 事件，失败回退通用兜底）；
- **顶栏模型切换器**：同服务商下拉即生效；跨服务商引导去配置页填新 Key（**Key 不通用**，防静默用错）；
- **配置错配事故 → 显式上报**：配置切回 deepseek-chat 但 Key 还是小米的，全部回答静默为空。修复：新增 `error` SSE 事件——LLM 失败/空回答在卡片内显示真实原因与处理指引，检索失败同样上报；设置页换服务商未填新 Key 时显式提醒；
- **容量规划**（`bench_ingest.py`）：实测小文档 ≈0.15s/份、大文档 ≈0.5s/份，外推千份约 5~10 分钟，4 核 8G 足够；31 份 .doc 当时不在支持列表需先转换（v3.1.0 解决）。

### 5. 对话历史合并进问答页（v2.6.0）

- 独立「对话历史」页下线，功能并入智能问答：顶栏「历史」滑出抽屉（会话列表 / 跨会话搜索按会话去重 / 勾选批量删除 / 点击无缝续聊切换 SESSION_ID）；
- 抽屉打开时实时刷新，新问答完成同步更新。

## 三、踩坑与修复

1. 缺必填提交返回 500：`qa.py` 漏导入 `HTTPException` → 修为 400；
2. 配置错配静默空回答（见上）——修复方向不是「防止用户配错」，而是**配错时把真实原因递到用户眼前**；
3. 意图分类误判：「请假流程」纯咨询被判成 action 走非流式 → `_refine_llm_intent()` 规则后置校验。

## 四、产出物

多服务商热切换体系（test/save 分离 + models 拉取 + 顶栏切换器）；流式延迟治理四步法（6.9s）；卡片式回答 UI + SSE 阶段事件 + error 事件；流程确认闭环（draft/submit + 工单卡）；bench_ingest 容量基线；测试 46 → 52。

## 五、教训与规约

1. **流式延迟治理方法论**：先分段测量 → 消除调用次数（合并/免调用）→ 降级重调用（关思考）→ 全程状态可视化。直觉上「模型慢」，实测里辅助调用次数才是大头；
2. **结构化输出优于自由文本解析**：`with_structured_output` + Schema 校验 + 正则兜底，三层防幻觉参数；
3. 换服务商必须连带检查 Key——「配置错配」不是边缘 case，是必然会发生的事故，设计上要让它**可见**；
4. 容量问题用 bench 脚本实测外推，不拍脑袋；基准脚本要隔离临时库可复跑。
