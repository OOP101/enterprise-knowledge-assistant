## 一、阶段目标

用 AI 代码审查工具对整个代码库做一次**交付前体检**，并守住一条底线：

> **只修「回源码核实成立」的问题；工具报了但站不住的，一条不改。**

理由很实际：这类工具的输出**看起来都很像真的**（带行号、带建议 diff），照单全收会引入无谓改动、破坏既有正确实现，还会消耗大量 review 时间。所以本次的真正工作量不在"跑扫描"，而在**逐条回源码复核**。

## 三、修复的关键问题（重点）

### 3.1 P0-1 用户表可能被静默清空（本次最严重）

`src/auth/users.py` 的 `_load()` 原实现：

```python
except Exception:      # noqa: BLE001
    self._users = {}   # ← 解析失败 = 当成"没有用户"
```

**后果链**：`users.json` 一旦损坏（半截写入 / 编码错 / 磁盘满）→ 不报错、内存用户表被清空 → **随后任意一次写入都会把空表覆盖回磁盘 → 全部账号永久丢失且无任何痕迹**。这是"静默失败"最贵的一种形态：不报错、不可逆、事后无法归因。

**修复**（三层防护）：

1. **ERROR 日志**（带完整堆栈），不再是静默；
2. **备份原始文件**为 `users.json.corrupt-<时间戳>`（保留原始字节，便于人工抢救）；
3. **进入只读降级模式**：`_save()` 抛 `RuntimeError` 拒绝任何写回，**原文件绝不被覆盖**。

> 判据：`RuntimeError: 用户表处于只读降级模式` **不是 bug，是保护生效**——去修原文件再重启。

### 3.2 P0-2 弱口令可被设置 → 黑名单

新增 `_WEAK_PASSWORDS`（9 个，含项目自带默认值 `admin123`），`_validate_password()` 直接拒绝。目的是防"改了文档没改 `.env`"这类**回归**——默认值本身不可怕，可怕的是它随时能被重新写回去。

### 3.3 P0-3 启动自检会漏判（一个容易踩的配置陷阱）

原自检只比对 `settings.admin_password == "admin123"`。但：

> ⚠️ **预置管理员账号一旦已存在，改 `.env` 的 `ADMIN_PASSWORD` 就完全不再生效**——该设置只在"账号不存在时创建"那一刻起作用。

所以只查设置值会**漏判真实风险**（`.env` 看起来改了，账号口令还是老的）。修复为**回查账号本身**：`store.verify(admin_username, "admin123")`。

### 3.4 P1 静默失败整改：17 处清零

项目自身规约写着「**静默失败是头号敌人**」（见 [08 篇](./08-v3.0.1-v3.1-静默丢弃修复与格式扩展.md) / [11 篇](./11-开发规约与环境基线.md) §五），而全仓仍有 **17 处 `except ...: pass/continue`**。本次全部补上日志并统一口径：

| 场景 | 级别 | 理由 |
|---|---|---|
| 探测 / 读取失败可降级（查重、定位 doc_id、读分片哈希、读原文缓存、SSE 事件解析…） | `debug` | 有明确兜底语义，但必须留痕 |
| 写入 / 删除失败会留脏数据（删分片、删文档、清查询缓存、写记忆、写配置…） | `warning` | 会造成数据不一致或"看起来成功" |

覆盖：`serve/routers/qa.py`（对话历史保存、追问建议、SSE 解析）、`src/agent/agent.py`（长期记忆写入、意图分类）、`src/agent/react_agent.py`（记忆读写、工具结果 sources 解析）、`src/agent/workflow_chain.py`、`src/chains/*`、`src/auth/deps.py`、`serve/routers/knowledge.py`、`serve/main.py`（chroma 段自愈）、`src/models/llm.py`（模型配置读写）、`src/review/store.py`、`src/ingestion/embedder.py`（10 处）、`launcher.py`。

**其中一处特别值得记**：`src/chains/context_compressor.py` 的 LLM 摘要压缩失败原为 `logger.debug` 后回退规则截断。这意味着**压缩链路悄悄降级、却没人能发现**——而「压缩率 21%」这个对外口径正是来自正常路径，长期失效会让口径失真。已升为 `warning`。

### 3.5 P1 并发安全：5 处加锁

`src/core/container.py` 的 `_get_or_create()` 是裸的「查-判-写」。FastAPI 同步端点跑在**线程池**里，并发首访会同时进入"key 不存在"分支 → **重复构造 BGE / Chroma**（模型重复加载 = 内存翻倍，且两个实例各持缓存互相覆盖）。改为锁内构造；同理 4 个模块级单例（`get_user_store` / `get_chat_history_store` / `get_review_store` / `get_feedback_store`）全部改双检锁。

### 3.6 P2 顺手项

- `src/agent/workflow_chain.py`：系统提示硬编码 `今天是 2026-08-30` → 改 `datetime.date.today()`（长期运行必然算错日期）；
- `src/eval/metrics.py`：F1 计算去掉浮点等值比较 `h + p == 0`，改用非负比率的 `h <= 0 and p <= 0`。

## 四、踩坑与决策

### 4.1 工具的四种误报模式（记住可省一半工）

| 模式 | 本次实例 | 反制 |
|---|---|---|
| **只看路由层，不看 store 层** | 报「路由把 URL 里的 `session_id` 直传后端 → 会话越权」×4（high）。实际 `chat_history.py` 全部方法签名是 `(username, session_id)`，路径**恒**为 `{base}/{username}/{session_id}/`，另有 `_bind_session` 把 session_key 绑成 `username:session_id` → **双重隔离，越权不可达** | 一定要去读被调用方 |
| **审 security 但不读验证逻辑** | 报「JWT 算法混淆 / `alg=none` 攻击」×4（high）。实际 `decode_token` 恒用 `hmac.compare_digest(_signature(...))`，`_signature` **硬编码 HMAC-SHA256，从不读 `header["alg"]`** | 读验证函数本体 |
| **把 `logger.exception` 当"未处理"** | 报某模块 3 处「异常被吞、未重新抛出」（high）。实际这 3 处**本来就是 `logger.exception(...)`**（带完整堆栈），只是被 `except Exception` 模式匹配误判 | 看 except 体里到底写了什么 |
| **不区分「服务端配置」与「用户输入」** | 报「`_http_launch` SSRF」（high）。实际 host 来自服务端 `settings.workflow_api_base`（只有 path 段可污染），且该项默认空字符串 → **默认配置下该分支根本不执行** | 追变量来源 |

**其余同类误报**：上传路径穿越（`safe_filename = Path(name).name` 已剥离目录成分）、`settings_ready` 的 NameError（同模块 line 113 定义，Python **调用时**解析全局名，定义顺序无关）、`token_tracker` "文件写在锁外"（`record()` 在 `with self._lock:` 内调用 `_append`）、`feedback.py` "读改写非原子"（读+写**整段在锁内**）、`delete_document` "缺 KB 校验"（`can_access_kb` 里 **admin 恒返回 True**，设计如此）、`register` "角色提权"（早有 `is_admin_caller` 守卫）、`context_compressor` "截断乱码"（Python `str` 按**码点**切片，不会切坏 UTF-8）。

> **决策**：以上 15 条**一条不改**，但全部写进交付记录并附源码证据——**误报清单和待改清单一样有价值**，它解释了"为什么这里不需要动"。

### 4.2 ⚠️ 加锁必须用 `RLock`（本次实踩）

给容器加锁时差点引入一个比原 bug 更严重的问题：

> `get_retriever` 的工厂**内部**会嵌套调 `get_reranker()`，`get_vector_memory` 嵌套调 `get_embedding()`。
> 若用 `threading.Lock`（不可重入）→ **当场自锁死**，服务起不来。

结论：**容器/单例加锁一律用 `RLock`**；并加回归用例 `test_container_nested_factory_does_not_deadlock`（子线程 + `join(timeout=5)`）守住这个陷阱——否则下次重构会再次踩进去。

### 4.3 改 Markdown 结构性标题会"吞标题"（工具坑）

用精确替换改 `CHANGELOG.md` 时，替换串以 `---` 结尾、原文以 `---\n\n## v4.0.0 — …` 开头，结果**整个版本标题行被吃掉**，v4.0.0 的内容一度挂到了新版本下面。

**教训**：改结构性标题（`## vX.Y.Z` 这类）时，替换串**首尾都要留不参与替换的锚点行**；改完必须 `grep -n "^## "` 回读校验——**信验证，不信工具的返回值**。

### 4.4 凭证类发现的处置边界

审查确认了两个真实高危项：管理员账号口令仍是默认值、JWT 签名密钥低熵可猜。但**改动 `.env` 属于改用户配置**，因此本次的处置是：

- **不擅自改**，把决策权交给用户；
- 交付一个**默认 dry-run 的一键脚本**（`scripts/rotate_admin_password.py`：自动备份 `.env`、`--apply` 才落盘、新口令只打印一次、同时重置账号——因为只改 `.env` 对已存在账号无效）；
- 启动自检照旧告警（并且如 §3.3 所述修好了漏判）。

## 六、教训与规约

1. **AI 审查工具是"线索生成器"，不是"缺陷清单"。** 实测 high 档误报率约 55%，且**质量越高越像真的**（带行号、带建议 diff）。**任何一条引用前必须回源码核实**，尤其 security / critical 级。反过来也成立：**它也会漏真 bug**（本次真问题里，最严重的用户表清空是靠读代码发现的形态，而不是报告直接指出）。
2. **给工具喂"项目自己的规约"，召回会变准。** 本次在规则文件里写明项目栈、业务背景与已知缺陷史后，它大量命中了违反「静默失败是头号敌人」的 `except: pass`——**这是本项目最有价值的一类自动化检查**，可考虑纳入日常（不耗 token 的 lint 无法覆盖）。
3. **降级路径的日志级别要匹配后果。** "可降级"不等于"可以不吭声"：**读取失败可以 `debug`，写入/删除失败必须 `warning`**。口径失真往往就出在这里（见 §3.4 压缩链路）。
4. **加锁前先看工厂里有没有嵌套调用**——有就是 `RLock`。这类"修复引入新缺陷"比原缺陷更危险，因为它在启动时就崩。
5. **改文档结构性内容后必须回读校验**（§4.3）。工具的"成功"不等于"改对了"。
6. **对外的数字必须能复现**：本次发现 `代码规模` 一栏（旧写 74 文件 / 7306 行）**无法复现**，已按可复现口径重测并写明方法（见 [11 篇](./11-开发规约与环境基线.md) §三）。
