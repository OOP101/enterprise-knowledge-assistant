## 三、口径单一事实源（防止多副本打架）

同一类数字在多个文件里出现是**有意为之**（不同场景要不同的详细度），但必须**有唯一权威来源**。改动时先改权威来源，再同步副本。

| 口径类别 | 权威来源 | 副本位置 |
|---------|---------|---------|
| 实测数据口径（测试数 / 文档数 / 分片数 / 压缩率 / 冷启动…） | `开发手册/11` §三 | `项目文档.md` §九、`简历面试/面试备考手册.md` §二 |
| 已证伪口径（"压缩 60%"、"首字 1.3s"、"scrypt 50ms"…） | `开发手册/11` §四 | `项目文档.md` §九尾注 |
| 已知限制 | `开发手册/11` §六 | `项目文档.md` §十 |
| 依赖矩阵（langchain 版本锁） | `开发手册/11` §一 | `requirements.txt` |
| 版本变更细节 | `../CHANGELOG.md` | `项目文档.md` §七、`开发手册/README.md` §一 |
| 架构链路 / 目录结构 | `项目文档.md` §三、§六 | `../README.md` |
| UI 改版范围与验收 | `UI改版需求文档.md` | `开发手册/10` §一、`../CHANGELOG.md` v4.0.0 |

> **规约**：无实测出处的数字不写进文档；规划值必须标注「规划 / 未实测」，实测后全文替换。

## 四、冗余清单（同一条信息的多份副本）

结论先说：**没有一份整份多余、该删的文件**。冗余全部是"同一条信息被写了多遍"，且每遍面向不同读者。因此**不建议物理合并**（合并反而会破坏"入口层 / 复盘层 / 流水层"的分工），正确做法是上面的第三节——认权威、其余留指针。

| # | 冗余内容 | 出现在 | 处置建议 |
|---|---------|--------|---------|
| 1 | **实测数据口径表** | `开发手册/11` §三（12 项，超集）· `项目文档.md` §九（11 项，子集）· `面试备考手册` §二（子集） | 保持现状；以 11 篇为准 |
| 2 | **已知限制清单** | `开发手册/11` §六（5 条）· `项目文档.md` §十（3 条） | 保持现状；11 篇为超集 |

## 六、维护约定

1. **数字留痕**：任何写进文档的数字都要有实测出处，标注测量日期与测量方式（建议照抄 `开发手册/11` §三 的"校准说明"列格式）；
2. **先改权威、再同步副本**：见第三节表格；同一口径改动要一次性同步 `项目文档.md` / `README.md` / 简历侧；
3. **新阶段开新篇**：每完成一个版本阶段，在 `开发手册/` 追加一篇（统一结构：阶段目标 → 关键动作 → 踩坑与决策 → 产出物 → 教训与规约），并更新 `开发手册/README.md` 总时间线；
4. **截图入库前量化压缩**：256 色 PNG，单张控制在 ~110 KB 以内；命名小写英文。
